# Proposed stack

This is the Phase 1 decision. The evidence is in [infrastructure-audit.md](infrastructure-audit.md). There is one primary stack, and a component gets swapped only when measured failures require it.

## Decision

Build a **headless Node/TypeScript bot on Mineflayer against a vanilla Java 1.21.4 server**. Navigation goes through mineflayer-pathfinder behind our own adapter. Progression logic follows AltoClef's design: a deterministic task tree plus priority survival interrupts, written as small typed skills. A thin evaluator runs fresh random-seed worlds with minecraft-wrap.

Why not the AltoClef/Baritone client-mod route, which is proven? It needs a real game client per run, its maintenance is split across hobby forks, it is Java-mod development, and it is hard to batch or inspect. Its only real advantage is Baritone's navigation. We keep that option open through the navigation adapter and the miner-org fallback rather than paying the client-mod cost up front.

## Exact stack

| Layer | Component | Version / pin |
|---|---|---|
| Runtime | Node **22 LTS** (pinned via `.nvmrc`; Node 26 is installed locally, but native `gl` builds lag behind) | ≥ 22 required by Mineflayer |
| Language | TypeScript, run with `tsx`; tests with `vitest` or `node:test` | — |
| Game | **Minecraft Java 1.21.4**, official vanilla server jar, Java 21 | Exact version pinned |
| Server control | `minecraft-wrap` | ^1.10 |
| Client | `mineflayer` | 4.39.x exact |
| Navigation | `mineflayer-pathfinder` from a **git commit on master** plus `patch-package` patches (lava, doors) | commit SHA pinned |
| Resource gathering | `mineflayer-collectblock` (brings `mineflayer-tool`) | exact |
| Survival | `mineflayer-auto-eat` v5, `mineflayer-armor-manager` | exact |
| Melee | `mineflayer-pvp`, vendored if its tick-event bug persists | exact |
| Crafting | Mineflayer's built-in crafting plus `mineflayer-crafting-util` if it passes tests; otherwise a small custom resolver | — |
| Visuals (optional) | `prismarine-viewer` (browser view for humans, headless frames for failure bundles) | `optionalDependencies` |
| Planner model (optional, off by default) | Anthropic SDK, strong model at decision/failure boundaries only | added in a later milestone |

**Why 1.21.4:**
- It is in Mineflayer's CI-tested set.
- It is the newest version with native prismarine-viewer assets.
- It is covered by Mindcraft's field use, which runs up to 1.21.11.
- It runs on the installed Java 21.
- It avoids 26.x, whose support is only weeks old.

Pin it and don't chase new releases.

**Server settings:** `online-mode=false`, `difficulty=normal` (confirm and record in `evaluation.md` before the first gate), default gamerules (no keepInventory), no ops, and `level-seed` generated by the evaluator. Evaluator-only process control goes through server stdin. The bot never gets operator access.

## Architecture

```text
Evaluator (Node, minecraft-wrap)
  ├─ creates world with private random seed, starts vanilla 1.21.4 server
  ├─ spawns bot process; enforces timeout; tails server log for ground truth
  └─ writes runs/<id>/{summary.json, events.jsonl, failure/}      (seed kept in runs/<id>/private/)

Bot process
  Mineflayer + plugins                    ← mechanics: protocol, physics, dig/place, windows, eat, armor
    └─ NavigationAdapter                  ← goto(goal, opts) → {ok | reason}; stuck/lava/timeout detection
         └─ Skills (deterministic)        ← collect, craft, smelt, fight, build portal, find fortress,
                                            barter, triangulate stronghold, fill frame, kill dragon
              ├─ Observer                 ← compact JSON state + event stream (+ optional frame)
              └─ Controller
                   ├─ Survival interrupts ← lava/fire/drowning/hunger/hostiles/night (always preempt)
                   ├─ Progression tree    ← milestone predicates on inventory/dimension (AltoClef-style)
                   ├─ Recovery policy     ← deterministic: retry → relocate → alternate method → abandon
                   └─ Advisor hook        ← optional strong model; picks from a validated menu of skills
  Local control endpoint (localhost only) ← observe / pause / resume, for coding agents and humans
```

### Responsibilities and interfaces
- **Skill contract** (from AGENTS.md): `run(params, ctx) → { outcome: 'success'|'failure'|'timeout', reason, evidence }`. Each skill has explicit preconditions and a timeout. Skills never call the model.
- **NavigationAdapter** is the only code that touches the pathfinder. That makes swapping in `@miner-org/mineflayer-baritone` a single-file change, and it keeps stuck detection and failure reasons consistent across implementations.
- **Observer** emits a fixed schema: position, dimension, health/food, inventory summary, equipment, nearby hazards and hostiles, current goal and skill, and the last N events. The controller, the logs, the advisor and the inspector CLI all read this same schema.
- **Controller** is plain deterministic code. The **advisor** is called only when the recovery policy has run out of options or a progression decision is truly ambiguous. It receives the observer snapshot and a failure summary, and must return a choice from a whitelisted skill menu, which is validated before use. With no API key, the deterministic fallback runs, so the first playable version needs no paid API.
- **Evaluator** is separate from the bot. It owns the seeds, timeouts, ground-truth parsing, artifact collection and aggregate reports. It also runs **fixture scenarios** that use commands to set up a state (for example, "start in the Nether with gear") to test late-game skills. Those runs are labeled as fixtures and never count toward gates.
- **Coding-agent access:**
  - Run artifacts are plain files: JSONL events, `summary.json`, and a failure bundle with state, recent events and an optional frame.
  - An `inspect` CLI summarizes a run or a batch.
  - The localhost endpoint serves live observation.
  - An MCP wrapper is optional and can come later.

### Dependencies between components
Evaluator → (server, bot process). Bot: Controller → Skills → NavigationAdapter / Mineflayer plugins → Mineflayer. Observer reads Mineflayer and the skill events, and has no dependencies back into the controller. Advisor → Observer schema only.

## What remains custom
1. Evaluator plus inspector CLI (small).
2. Observer schema and event log (small).
3. NavigationAdapter with stuck/hazard detection (medium).
4. Progression skills with no library equivalent (the core of the project):
   - obsidian (bucket casting or diamond pickaxe) and portal build
   - Nether fortress search and blaze kills
   - pearls from endermen or piglin bartering
   - eye-of-ender triangulation
   - stronghold dig-in and frame fill
   - End: crystals and dragon (bed strategy)
5. Controller: survival interrupts, progression tree, deterministic recovery (medium).
6. Advisor hook (small, later).

Everything else (protocol, physics, inventory/windows, digging, placement, crafting recipes, pathfinding, eating, armor, tool choice, melee, rendering, server lifecycle) is reused.

## Version and compatibility constraints
- Mineflayer, minecraft-data and the server jar must all be the same version, **1.21.4**. Set `version: '1.21.4'` explicitly on the bot.
- Mineflayer needs Node ≥ 22. The native viewer dependencies (`canvas`, `gl`) must stay optional.
- mineflayer-pathfinder's npm release is too old; pin a master commit and keep patches in `patches/`.
- Commit the lockfile. Before bumping any dependency, rerun the navigation benchmark.
- Licenses: all runtime dependencies are MIT/ISC/BSD. GPL/AGPL/unlicensed candidates were rejected.

## Largest technical risks
| Risk | Mitigation |
|---|---|
| **Navigation reliability** (lava, Nether terrain, caves, water, getting stuck) is the most likely leading failure | Adapter with stuck/lava detection and consistent failure reasons; pathfinder patches from Mindcraft's known issues; a **navigation benchmark on fresh seeds** early; miner-org fallback behind the adapter |
| Long-horizon runs (hours each) make evaluation slow | Parallel servers on separate ports; gate on stage metrics (time to iron, portal, blaze rods); fixture scenarios for late stages |
| Finding structures without cheats (fortress, stronghold) | Established methods: exploration spirals over loaded chunks, eye triangulation, bartering as an alternative to fortress pearls; AltoClef as tactic reference |
| Combat deaths (lava, blazes, endermen, dragon) | Survival interrupts first; armor/shield/water bucket as progression prerequisites; bed-explosion dragon strategy |
| prismarine-physics diverging from vanilla | Pinned version; vanilla server; tolerate `forcedMove`; log physics anomalies as a failure category |
| Upstream drift, unreleased fixes | Exact pins, lockfile, patch-package, benchmark before bumping |
| Native screenshot dependencies breaking | Viewer is optional; JSON observation is always primary |
| Overfitting to development seeds | Separate held-out seed set; no seed data visible to the bot; fixes must address failure categories, not individual seeds |

## First implementation slice (Phase 3)
A **walking skeleton that closes the evaluation loop**, which is milestone M0 in [milestones.md](milestones.md):
1. The evaluator creates a fresh random-seed vanilla 1.21.4 world, starts the server, spawns the bot, enforces a timeout, parses the server log, and writes `runs/<id>/` artifacts. The seed is stored privately.
2. The bot connects, and the observer emits the schema and event stream.
3. The NavigationAdapter plus one skill chain: collect logs → craft planks → crafting table, with outcomes and failure reasons.
4. An `inspect` CLI for a run and a batch.
5. Run **10 unattended fresh seeds** and report counts and top failures.

Right after that, build the **navigation benchmark**: random reachable targets at a range of distances, surface and cave, on fresh seeds. It decides early whether mineflayer-pathfinder is good enough, which is the single biggest open question for the stack.

## Cross-check
- **Custom code is minimal:** every mechanic with a maintained library is reused. What is left is the progression knowledge no library provides, plus thin glue.
- **There is a realistic path to a full clear:** AltoClef showed that a deterministic task tree with survival interrupts can beat the game using client-visible information only. This stack reproduces that architecture on a headless client that is easier to test. The main gap compared with AltoClef is navigation quality, which is isolated behind one adapter and measured first.
- **The run rules hold:** no commands, ops, seed access or fixed coordinates in scored runs. Commands appear only in labeled fixture scenarios run by the evaluator.
